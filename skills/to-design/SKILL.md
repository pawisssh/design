# To-design

Builds a Component Family in a Figma Design Library from its Contract, in this order:

1. **Foundations**: Variable collections, modes, variables and Text Styles from the foundations document.
2. **Icons**: one icon atom component per icon the Contracts name.
3. **Base loop**: the Base Component alone, read back and diffed after the owner's tweaks, until the owner approves the Contract in chat.
4. **Batch build**: the whole Component Set from the approved Contract, in batches.
5. **Verify**: coverage, sample and theme checks of the set against the Contract.
6. **Publish**: the owner's step, in Figma.
7. **Code Connect**: after publish.

Steps 1-5 run the same way: derive a plan, package it, send it to `use_figma`, record the result. A run never writes builder code: the cores are fixed, and a run changes only the build plan and the ledger.

## Before you start

- **A Contract** in `design-systems/<ds>/contracts/<family>.component.json` that passes `node skills/contract/scripts/check.mjs <component.json>` (it prints `OK`). It may be a draft: To-preview is optional. Contracts come from an Adapter skill (Carbon: [`adapter-carbon`](../adapter-carbon/SKILL.md)).
- **The foundations document** next to `contracts/`, regenerated by the Adapter after the last Contract change (a rerun leaves it byte-identical).
- **The Adapter's sources fetched.** Carbon: `node skills/adapter-carbon/scripts/sources.mjs`, which also unpacks `@carbon/icons@11.90.0` into `.scratch/adapter-carbon/sources/npm/@carbon/icons@11.90.0/package` for the icons slice.
- **The Design Library file key**: from its URL, `figma.com/design/<fileKey>/...`. Create a new file only when the owner asks. Every plan pins the key, and the core refuses another file (`wrong-file`).
- **The owner's go-ahead to write to that file.** Generating plans and packages writes nothing to Figma; only a `use_figma` call does.
- **The ledger**: `.scratch/to-design/<fileKey>.ledger.json` (gitignored), one per Design Library file. It maps names to Figma ids, so a rerun updates rather than duplicates. `build-plan.mjs`, `base-loop.mjs` and `coverage.mjs` read it from the project root (`$CLAUDE_PROJECT_DIR`, else the current folder) unless given `--ledger <path>`. `ledger.mjs record` writes it there, or to its `--ledger <path>`. Run every command from the project root. Run from a git worktree with `$CLAUDE_PROJECT_DIR` unset or set to the worktree, these commands refuse to run without `--ledger`, because the worktree's own `.scratch` would fork the ledger away from the main checkout's. The refusal prints the main checkout's ledger path: pass that same `--ledger <path>` to every command, `record` included.

## The call cycle

Every Figma step is the same five commands. `<run>` is a fresh folder per call, such as `.scratch/to-design/button-sets-1`:

```
node skills/to-design/scripts/build-plan.mjs <slice> ... --file-key <key> --out .scratch/to-design/<run>
python3 skills/to-design/scripts/package_native_builder.py skills/to-design/assets/<core> .scratch/to-design/<run>/plan.json .scratch/to-design/<run> --state .scratch/to-design/<run>/state.json
# use_figma with fileKey, description and code = the printed stub (Package delivery); save the returned JSON as:
#   .scratch/to-design/<run>/result.json
node skills/to-design/scripts/ledger.mjs record .scratch/to-design/<run>/result.json
```

- `<core>` is [`assets/builder-core.js`](assets/builder-core.js) for `foundations` and `icons`, and [`assets/builder-core-components.js`](assets/builder-core-components.js) for `base` and `sets`. A plan given to the other core returns `unknown-slice` or `package-mismatch` before any change. (One core holding every slice would not fit `use_figma`'s 50,000-char limit next to the foundations plan.)
- `use_figma` takes `fileKey`, `code` (at most 50,000 chars) and `description` (one line, such as "Button sets batch 1 of 5"). If the tool's own instructions ask you to load a Figma skill before calling it, do so; the cores need no authoring guidance from it.
- Save the call's JSON result before anything else. Record every result before deriving the next plan, so the next package carries the ledger Figma last returned. `record` refuses an error result; a result with `conflicts` keeps the old section.
- A read-only call (`--read-only`, or a sets read mode) needs no `record` unless this file says so.

### What a package is

[`scripts/package_native_builder.py`](scripts/package_native_builder.py) writes `build-components.mcp.js` (the core, the plan and state as `String.raw` text, a `CHECK` block of FNV-1a-32 hashes `{planLen, entries, plan, state, core}` and a top-level `return await ...`) and `script-package.json` (`fileSha256`, the check, `execution: not-run`). It refuses text with a backtick, `${` or non-ASCII, and it compacts the core (drops `//` comments and whitespace; strings are kept as written), so a core uses `//` comments only and no regex literals. Before its first change the core recomputes every hash; on a mismatch it returns `{error: "package-mismatch", field, expected, got}` and changes nothing. The cores run only in `use_figma`.

**The package never spells `<`.** `use_figma` transpiles any script whose strings hold markup-like text (`<svg`, `<p`, even the escape `<svg`). That reformats `buildComponentSets.toString()`, so the gate fails with a `core` mismatch before any change (found live in #30). The packager emits plan and state text that holds a `<` as `String.raw` pieces joined with `String.fromCharCode(60)`, and it refuses a core that spells markup-like text. Never hand-edit a package.

## Package delivery

The packager prints `chars`, `fileSha256` and a fail-closed `stub`:

```
/*@package .scratch/to-design/<run>/build-components.mcp.js sha256=<hex>*/ throw new Error("package not injected");
```

From a worktree the path starts with `.claude/worktrees/<worktree>/`. Copy the stub exactly as printed.

**Send exactly that stub as `use_figma`'s `code`. This is the default.** The PreToolUse hook [hooks/use-figma-package.mjs](hooks/use-figma-package.mjs) swaps it for the file after checking the sha256 against the stub and `fileSha256`, that the path stays inside the project, and that the package is at most 50,000 chars. It logs each swap to `.scratch/to-design/use-figma-package.log` in the main checkout. Verified live in #26: the conversation carries only the stub, and `use_figma` runs without a permission prompt, because the hook allows the call. Never re-type or paste a package when the stub works.

- **The path is relative to the main checkout** (git's main working tree), because the desktop host loads project hooks and sets `$CLAUDE_PROJECT_DIR` from the main checkout, also for a session in a worktree. The packager computes it, and refuses to write a package outside the main checkout: write it under the main checkout (a worktree under it works).
- **If the hook refuses**, it blocks the call with a one-line reason. Fix the cause and re-package; never edit the stub.
- **If `use_figma` returns `Error: package not injected`**, this session has no hook, and nothing changed in Figma. A session started before the hook was registered has none: project hooks load only at session start. Deliver the full contents of `build-components.mcp.js` as `code` instead (inline delivery). The core's integrity gate catches any drift in an inline copy before its first change.
- **The hook and its settings come from the main checkout.** A change to the hook or to `.claude/settings.json` takes effect only once it is merged into the main checkout, the checkout is pulled, and a new session starts. Registering the hook is the owner's step: they paste [hooks/settings.snippet.json](hooks/settings.snippet.json) into the project's `.claude/settings.json`. Agents never edit settings. `onFailure` needs Claude Code v2.1.295 or later. When the main checkout is behind its upstream on the hook or the settings, the hook still swaps, but warns that it is stale. Tell the owner to pull the main checkout and start a new session.

## 1. Foundations

```
node skills/to-design/scripts/build-plan.mjs foundations --doc design-systems/<ds>/<ds>.foundations.json --file-key <key> --out .scratch/to-design/<run> [--page <name>] [--adopt] [--prune a,b] [--chunk N]
```

Core: `builder-core.js`. It builds the Variable collections, modes, variables and Text Styles and follows the [update semantics](../contract/references/foundations-schema.md#update-semantics-idempotent): ownership through the ledger, `conflict` before any change, diff-based writes, mode order fixed with `setDefaultMode`, orphans kept until `--prune` with names the owner confirmed. The plan drops the document's review-only fields. Record the result: the ledger's `foundations.documentHash` gates every later slice, so rebuild foundations after every regeneration of the document that changed it.

The plan holds only the file's [subset](../contract/references/foundations-schema.md#to-design-builds-a-subset) of the document: the closure, the owner's groups (Spacing and Size by default) and every alias and bind target they reach (ADR 0006). The owner changes the groups with `node skills/to-design/scripts/ledger.mjs groups --doc <foundations.json> --file-key <key> --add <group> --remove <group> [--ledger <path>]`, then rebuilds foundations; a removed group's variables become orphans. When the output's `chunk.of` is above 1, the selection is over one call: run chunk 1, record it, then `--chunk 2` and so on, recording each before the next (a later chunk is refused until the earlier ones are recorded). Prune only with chunk 1.

## 2. Icons

```
node skills/to-design/scripts/build-plan.mjs icons --contract design-systems/<ds>/contracts/<family>.component.json [--contract ...] --icons-dir .scratch/adapter-carbon/sources/npm/@carbon/icons@11.90.0/package --file-key <key> --out .scratch/to-design/<run> [--page Icons] [--adopt]
```

Core: `builder-core.js`. It takes the union of the Contracts' icon lists (`icons()`: `icons.default`, `icons.preferred` and every fixed `icon:<key>` instance), reads each SVG (16 px file, else the 32 px fallback) and strips unpainted shapes (`fill="none"` or `opacity="0"`), such as the transparent bounding box. It builds one 16x16 component per icon on the Icons page: no fill, one flattened VECTOR named `Vector` with SCALE/SCALE constraints, kit-style name (`Arrow--right`), the source file in the description.

- Ownership is the same as for foundations, but there is no prune: a dropped icon becomes an orphan and is never deleted.
- A rerun reverts hand edits to the name, description, size, fill, page, and the Vector's name and constraints. It does not compare the Vector's geometry or fill.
- A changed SVG sha256, or a component reclaimed with `--adopt` (no recorded sha256), rebuilds only the Vector, so the component keeps its id and key.
- The ledger's `icons.components[key]` holds `{id, key, file, sha256}`: the key is what INSTANCE_SWAP `preferredValues` need, the id is the property default.

## 3. Base loop

The Base Component (every axis at its default) is built alone on the Contract's page, so the owner can tweak it in Figma. Each tweak is read back and written into the Contract, and the base is rebuilt from the Contract until it reads back clean. Then the owner approves.

```
node skills/to-design/scripts/build-plan.mjs base --contract <component.json> --doc <foundations.json> --file-key <key> --out .scratch/to-design/<run> [--read-only] [--page <name>] [--adopt]
# package with builder-core-components.js, use_figma, save result.json, ledger.mjs record (not after --read-only)
node skills/to-design/scripts/base-loop.mjs readback .scratch/to-design/<run>/result.json --out .scratch/to-design/<run>/readback.json
node skills/to-design/scripts/base-loop.mjs diff <component.json> .scratch/to-design/<run>/readback.json
```

The base plan resolves everything in node, so the core never matches rules. It refuses a Contract that fails validation, and a foundations document whose `documentHash` is not the one the ledger built. The core builds the anatomy inside one COMPONENT, binds tokens through the ledger's ids, writes a field only when the read value differs, and rebuilds the layers inside the same component when the tree differs (the id and key stay). Standing alone, the base is the review specimen: every BOOLEAN on, TEXT and INSTANCE_SWAP at their defaults. The ledger's `bases[family]` holds `{page, id, key, name, snapshotId, contentHash, documentHash, builtAt}`. The readback sets `figma.skipInvisibleInstanceChildren = false` and reads effects in order.

The loop:

1. Build the base and record. Send the owner the node link and ask them to tweak it in Figma, then tell you when they are done.
2. Read it back: `base` with `--read-only`, then `readback` and `diff`. `diff` lists token edits, raw edits, detached bindings, unmapped changes and fields it could not read. An empty diff means Figma matches the Contract.
3. Write the edits with `base-loop.mjs apply <component.json> <readback.json> [--confirm Node.field,...|all]`. Each mapped change lands in place in the rule that set the field, with `by: "owner"` and the old value in `was`. When the value is a [Drafted value](../contract/references/contract-schema.md#drafted-values), its `drafted` entry becomes `{by: "owner", was}`. Run it first without `--confirm`: when an edit hits a rule other variants share, it writes nothing and names each one with its blast radius (`ask the owner first: Button.gap changes 147/245 variants ...`). Ask the owner, then rerun with `--confirm` naming only the edits they agreed to (or narrow the rule by splitting it, as the owner decides). A typed number that equals exactly one token is offered as that token, never swapped in. An unmapped change (such as `letterSpacing`) becomes a `warning` note, which blocks approval; a derived raw the edit may have made stale gets a `verify` note.
4. Regenerate the foundations document if an edit introduced a new token, rebuild foundations if its `documentHash` changed, then rebuild the base from the edited Contract (back to step 2) until `diff` is empty.
5. If the owner drops a tweak the Contract cannot express, run `base-loop.mjs discard <component.json> <readback.json> --note <at>` once a rebuild reads back clean. It turns that `warning` note into `info`.
6. Review: `base-loop.mjs review <component.json> <readback.json> --file-key <key>` prints the review package (node link, `snapshotId`, `contentHash`, the diff summary, every edit with by/was, blast radius and shields, and the Drafted values by kind, the most taste-prone first: icons, property labels and defaults, grid, layout width) and the approve command. Show it to the owner.
7. Only after the owner types "approve" in chat: `base-loop.mjs approve <component.json> <readback.json> --snapshot-id <id> --content-hash <hash>`, with the values the owner reviewed. It needs a clean readback, the Base Component's name and no open `warning` note. Only the owner approves; `--prototype` writes `by: "orchestrator (prototype)"`, and only to an `--out` under `.scratch/`.

Every Contract write (`apply`, `discard`, `approve`) keeps the file's layout, so a diff shows only the edited lines. `base-loop.mjs regen skills/to-design/tests/fixtures/base-loop skills/to-design/tests/fixtures/base-loop/expected` rebuilds the test goldens from saved readbacks byte-for-byte.

## 4. Batch build

```
node skills/to-design/scripts/build-plan.mjs sets --contract <component.json> --doc <foundations.json> --file-key <key> --out .scratch/to-design/<run> --batch <N> [--per-call 49]
```

Core: `builder-core-components.js`. `sets` takes an approved Contract only: it refuses a draft, a failing validation, and a foundations document the ledger did not build. It expands the selection with the shared Contract module, resolves every tuple in node (identical fragments deduped), and packs each entry as an axis-ordered tuple of value indexes that decodes back to the approved selection. The selection is sparse: omitted variants are never built.

- **Batches.** Batch `N` (from 0) holds `PER_CALL` (49) entries in expansion order; the derive prints `options.batch` and `options.of`. Run batch 0, record, then batch 1, and so on to `of − 1`: one call per batch, never one per variant, and never two calls at once.
- **Base first.** When the ledger has `bases[family]`, the Base Component is moved into the set and rebuilt in place (same id and key) at the property defaults, and batch 0 holds it. No tweaked scratch copy stays behind.
- **Diffs only.** Writes happen only where the readback differs, so a rerun creates and updates nothing.
- **Batch ids only.** A call carries and returns only its batch's variant ids. `ledger.mjs record` merges them into `sets[family].variants` (one id per expansion index) and keeps the other families.
- **Lost connection.** A call whose result was lost may still have committed. Before retrying, run `--mode reconcile` (read only: it finds the set's variants by name, and reports the ones the selection dropped), record its result, and only then re-derive and retry the batch.
- **After a Contract edit** (a new omit, a re-approval), rebuild every batch, then see [Dropped variants](#dropped-variants-orphans-and-prune) below.

**The Figma structure** (checked by `coverage.mjs`):

- One page per family (`figma.page`, plural). On it a `Components` frame, VERTICAL, at least 2560×1440, with two children: `Header` and `Content` (padding 80, gap 80).
- `Header` is an instance of the `Component Header` template (TEXT properties Type, Title, Namespace from `figma.header`), built once on a `Templates` page.
- `Content` holds the COMPONENT_SET, a Grid Auto Layout: `figma.grid.columns` (Size) make the columns, `figma.grid.rows` (Kind then State) the rows, each axis default-first so the default variant sits top-left. Gap 20×20, padding 20, dashed stroke `#9747ff` (dash 10, gap 5), radius 5.
- Variants are named `Prop=Value` with the axis and value labels. TEXT, BOOLEAN and INSTANCE_SWAP properties are wired with `componentPropertyReferences`; the INSTANCE_SWAP `preferredValues` are the ledger's icon keys and its default is the icon id.

**Measured live (#32, 245 and 539 variants, 49 per call):**

- **Package size.** Packages run 40-47K chars, so 64 per call left too little room under 50,000.
- **Output.** Build output is at most 2.3KB. A coverage read is about 1.5KB plus 23 bytes per variant (6.6KB at 245, 13.1KB at 539); `use_figma` output must stay under 20KB, so one coverage read holds about 800 variants. A sample read is about 1.6KB per variant (keep it to 12 or fewer); a theme read is about 0.35KB per variant.
- **Time.** A creating call costs about 1.6 ms × variants created × set size: 5.1s at 49, 18.6s at 245, 41.8s at 539, so building a family is quadratic (539 variants took 263s over 11 calls). An update-free rerun call takes 0.4-1.1s, and a coverage read 0.3s at 539.
- **Ceiling: 49 per call.** At 49 the largest Button package measured 48,006 chars live (with the orphan flow of #67), and 64 per call at 539 variants would take about 55s, beyond the longest call measured. For a family above about 600 variants, lower `--per-call` so that 1.6 ms × per-call × set size stays under about 45s.

### Dropped variants: orphans and prune

A variant the new selection drops follows the rule for tokens that drop out of the foundations (ADR 0003): it becomes an **orphan** in the ledger and is deleted only through a prune list the owner confirms, after an instance count.

1. **Rebuild.** Every build call reports the set's children that the whole new selection no longer holds as `dropped` (`[name, id, key]`). `ledger.mjs record` moves each one whose id the ledger recorded from `sets[family].variants` to `sets[family].orphans` (`{<variant name>: {id, key, droppedAt}}`) and prints them as `orphaned`. A node the ledger never recorded is printed as `extra` and not tracked. Nothing is deleted. An orphan keeps the name it was dropped under; a dropped node a hand renamed before the rebuild is kept under the name it has. An orphan whose node a hand deleted leaves the list at the next build call. Finish a rebuild before the next Contract edit: the ledger keeps variant ids only for the current Contract, so a variant that a second edit drops before the first rebuild reached it is printed as `extra`, not tracked. Every build call lists every dropped node still in the set, orphans from earlier edits included, at about 100 bytes each (6.7KB of output in all with the 49 Focus variants dropped). A call stays under `use_figma`'s 20KB output up to about 180 of them, so prune before a set holds more. A child whose name no longer parses counts too, so an axis relabel or an added axis on a large set lists every old variant, and on a set of more than about 180 variants it can push a build call past the limit.
2. **Re-select.** When a later Contract selects a dropped variant again, the plan carries its orphan id, so the rebuild reuses that node (same id and key, renamed back if a hand renamed it). Recording the result removes it from the orphans.
3. **Coverage.** `coverage.mjs coverage` reads the ledger (pass `--ledger` from a worktree). It lists orphans under `orphaned`, by the name the ledger keeps, and does not count them as problems. It matches an orphan by its ledger id, so an orphan a hand renamed is still `orphaned`, and a node under an orphan's name that is not that node (made after a hand deleted it) is `extra`. Any other variant name it cannot find in the Contract is `extra` too.
4. **Preview** (read only, no `record`), once every batch is rebuilt from the current Contract:
   ```
   node skills/to-design/scripts/build-plan.mjs sets --contract <component.json> --doc <foundations.json> --file-key <key> --out .scratch/to-design/<run> --mode prune-preview
   ```
   The result's `orphans` maps each orphan to its instance count in this file, or `null` if its node is gone. Instances in other files (a published library's consumers) are not counted, and the result's `scope` says so. Show the owner the list.
5. **Prune list: the owner's decision.** Write it only after the owner names, in chat, the orphans to delete. This is the same as an approval:
   ```
   node skills/to-design/scripts/ledger.mjs prune-list .scratch/to-design/<preview-run>/result.json --name "Kind=Primary, Size=Large, State=Focus" [--name ...] --out .scratch/to-design/<run>/prune.json
   ```
   The list carries each count from the preview. It refuses a name that is not an orphan in the preview.
6. **Prune.** Derive with `--mode prune --prune-list .scratch/to-design/<run>/prune.json`, package, call, and record. The core refuses, before any change, a name that is not a ledger orphan (`not-orphan`) a name whose instance count differs from the list (`stale`), and an orphan a hand moved out of the set (`moved out of the set`). The preview refuses a moved orphan too. If a name is refused, preview again and ask the owner again. A moved orphan is no longer in the set, so the next build or reconcile drops it from the orphans and the preview runs again; the node itself stays where the hand put it. Otherwise it deletes only the listed nodes, and `record` drops them from the orphans. A prune call whose result was lost can be sent again with the same list: an orphan it already deleted counts `null` and is not `stale`.

## 5. Verify

Three read-only `sets` calls, each checked against the Contract by [scripts/coverage.mjs](scripts/coverage.mjs) through the shared Contract module:

```
node skills/to-design/scripts/build-plan.mjs sets --contract <component.json> --doc <foundations.json> --file-key <key> --out .scratch/to-design/<run> --mode coverage
node skills/to-design/scripts/coverage.mjs coverage <component.json> .scratch/to-design/<run>/result.json [--ledger <path>]
# likewise --mode sample --sample 0,17,42 (expansion indexes; keep to 12 or fewer) and --mode theme --sample ...
node skills/to-design/scripts/coverage.mjs sample <component.json> .scratch/to-design/<run>/result.json
node skills/to-design/scripts/coverage.mjs theme <component.json> .scratch/to-design/<run>/result.json
```

- `coverage`: every expanded variant exactly once, as a COMPONENT in its grid cell, with the default top-left; no missing, extra or duplicate variant (ledger orphans are listed under `orphaned`, not counted); property wiring, the set's property definitions, and the page, frame and Header above.
- `sample`: the chosen variants in full, diffed like the base (layout, paint, bindings, effects in order). Pick the base, one per kind and the extreme sizes and states.
- `theme`: each bound colour resolved in every mode of its collection, against the foundations document; the call restores the explicit modes.

Each prints `{ok, problems, ...}` and exits 1 on a problem. A hidden child of an auto layout reports FILL sizing as `FIXED`, so the readback takes fill from `layoutGrow` (main axis) or `layoutAlign: STRETCH` (cross axis). Packaging or parsing a script is never evidence of what Figma holds: report a step as done only from a recorded result and a passing check. Report the Figma link, the variant count built against the Contract's `expectedCount`, and the raw `warning` values the Contract carries.

## 6. Publish (owner)

The owner publishes the Design Library from Figma. Agents don't publish. Foundations stay local to the file for the pilot.

## 7. Code Connect (after publish)

Code Connect needs published components, so it runs only after step 6. The mapping comes from the Contract alone: the top-level `code` (`framework`, `package`, `component`, `import`, `alwaysEmit`) and the `code` beside each axis value and property (`lg-expressive` → `size="lg"` plus `isExpressive`; `renderIcon` from the Icon properties). On a Figma Professional plan Code Connect needs a Full or Dev seat and allows one active library and one framework (#4). No Code Connect tooling is built in this repo yet.

## Tests

`node --test skills/to-design/tests/*.test.mjs` runs every slice against a mock Figma (`tests/mock-figma.mjs`), the packager, the hook, the base loop and the coverage checks. The full suite, from the project root: `node skills/adapter-carbon/scripts/sources.mjs`, then `npm test`.
